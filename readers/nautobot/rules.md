# Rules of the Nautobot reader

Every finding the reader files has a stable dotted rule id, as the core's do (Constitution X),
and callers and tests match on the id, never on the wording. These rules are the reader's own,
never the core's, the Infrahub reader's or the NetBox reader's
([`formats/README.md`](../../formats/README.md), note 11); the core's are in
[`docs/rules.md`](../../docs/rules.md). A finding is the core's `Finding`, of findings 1's form
([`findings-1.schema.json`](../../formats/findings-1.schema.json)): its severity, as its object
the name in Nautobot of what it is about, and a message of one sentence that never holds a byte
of a configuration. A read whose findings hold an error gives no blueprint
([D-118](../../design/decisions.md#d-118)). The code names each rule by a module-level constant
beginning `RULE`.

A **problem** is a reason the reader document is refused, so that no read is made with it; the
problems' rows come first, their severity `problem` and their object the pointer. The
**findings** follow.

The catalogue holds every rule the code files; a test holds it to the code.

| Rule | Severity | Object | Means, and the remedy |
|---|---|---|---|
| `reader.version.unsupported` | problem | `/reader_version` | The document's `reader_version` is not `1`, and nothing else of it is checked. Write it in version 1's form |
| `reader.invalid` | problem | The member at fault (`/probes`); for a member missing or unknown, the object that lacks or holds it (`""` for the document, `/platforms/0` for a row), the member named in the detail; `""` for a file that is neither JSON nor YAML | The document violates its schema, or the file is no document at all. Correct what the detail names |
| `reader.platform.duplicate` | problem | The later row (`/platforms/1`) | Two rows hold one pair of manufacturer and platform, compared exactly, letter case and spacing included, so the pair would name two packages, or one package twice. Keep one row for the pair |
| `scope.invalid` | error | The scope as given (`site:x`) | The scope is not `tag:<name>` with a name, so nothing is sent to Nautobot. Give the scope as `tag:<name>` |
| `golden_config.absent` | error | `nautobot_golden_config` | `/api/status/`'s `nautobot-apps` names no `nautobot_golden_config`, and a device's configuration is Golden Config's render of it, so nothing more is sent: no list is read and no device rendered. Install the Golden Config app |
| `scope.empty` | error | The scope (`tag:fylgja`) | Nautobot lists no tag of the scope's name, compared exactly, letter case included, or no `dcim.device` carries it, so the scope selects no device and the result is `empty`. Tag the devices to read, or correct the scope's name |
| `read.incomplete` | error | The list, by Nautobot's object type: `dcim.device`, `dcim.platform`, `dcim.manufacturer`, `dcim.interface`, `dcim.cable`, `extras.tag`, `nautobot_golden_config.goldenconfigsetting`, `extras.gitrepository`, `extras.dynamicgroup`, `extras.staticgroupassociation` (a group's stored members), `extras.configcontext` (the probes' context, by its name) | A list Nautobot answered held other than the `count` it gave for it, or one object twice, or no object of an id it was asked for by id, so mapping it would give a blueprint of less than Nautobot holds. The message gives the numbers. Read again; a list that is still not whole is a fault of Nautobot's answer, to report with the list |
| `read.moved` | error | `extras.objectchange` for the changelog; a template repository's name (`fylgja-templates`) for its head | At the read's close the changelog's newest row is another than at its open (a row newer than the open's, another of the same time, or the open's none and any row now), or its total count differs (a row of an earlier time made visible late, at its transaction's commit, or one pruned), or a template repository a Golden Config setting names has another `current_head` or is no longer listed, so the read may hold two states of Nautobot, or renders of two commits. Every kind of row counts, the row a render writes when it fetches a moved head among them, so a push refuses one read and the next passes. The message gives both values. Read again |
| `nautobot.version.unverified` | warning | Nautobot's version and Golden Config's, `<version>/<Golden Config's>`, `none` where `/api/status/`'s `nautobot-apps` names no `nautobot_golden_config` (`3.2.9/3.0.8`, `3.2.8/none`) | The Nautobot read is of a pair of versions the reader was not verified on, none of `SUPPORTED` (Nautobot 3.2.8 with Golden Config 3.0.8). Every result of that connection carries it, and it is logged once, at the connect; the read goes on. Verify the reader on that pair, its contract tier against it, before relying on what it reads |
| `platform.missing` | error | The device's name in Nautobot (`n1`), or `dcim.device <id>` where it has none | The device has no platform, or its platform no manufacturer, so the reader document cannot choose its platform package. Give the device its platform, and the platform its manufacturer |
| `platform.unmatched` | error | The device's name (`n1`), or `dcim.device <id>` where it has none | The device's platform's manufacturer and name, compared exactly, letter case and spacing included, are a pair no row of the reader document holds. Add the pair's row to the document, or correct the names in Nautobot |
| `device.name.renamed` | info | The device's name in Nautobot (`N1`) | The device's name is no DNS-1123 label, so the blueprint names it by its label ([D-038](../../design/decisions.md#d-038)): lower-cased, each run of characters outside `[a-z0-9]` made one `-`, and `-` trimmed from both ends. A fidelity row whose source is `dcim.device.name` names both, and each link and probe names the device by the label. Rename the device in Nautobot to read its name unchanged |
| `device.name.unmappable` | error | The device's name (`***`), or `dcim.device <id>` where it has none | The device has no name or an empty one, or its name makes no DNS-1123 label: it holds no letter or digit, or its label is longer than 63 characters. Name the device in Nautobot, or rename it |
| `device.name.duplicate` | error | Each device's name (`N1`, and `n1`) | Two or more scoped devices make one label, so the blueprint could not tell them apart: each is filed, its message naming its own device first and then the others, and a name two of them hold exactly, with each one's id (`n1 (dcim.device 4)`). Rename all but one of them in Nautobot |
| `omit.cable.ends` | info | The cable, by its label, or `cable <id>` where it has none | A side of the cable has other than one termination, and a link has one a side. The cable is left out of the blueprint, a fidelity row `omitted` whose source is `dcim.cable`, and the rest of the network is read. Give each side of the cable one interface |
| `omit.cable.endpoint` | info | The cable, by its label, or `cable <id>` | An end of the cable is no `dcim.interface` (a `dcim.frontport`, say, a path through a patch panel), and a link ends on an interface. Left out, a fidelity row. Cable the two interfaces to each other |
| `omit.cable.outside_scope` | info | The cable, by its label, or `cable <id>` | An end of the cable is on no interface read of a scoped device, a device the scope does not hold, which is never read and is named by its interface's id, or on a virtual, bridge or LAG interface, which is no port. Left out, a fidelity row. Tag the far device to read the link, or cable a port |
| `omit.cable.management` | info | The cable, by its label, or `cable <id>` | An end of the cable is on an interface that is `mgmt_only`, and blueprint 1 refuses a link on one. Left out, a fidelity row. Cable a port that is not `mgmt_only` |
| `group.stale` | error | The dynamic group's name (`GoldenConfigSetting Default Settings scope`) | A scoped device is listed by the filter of a Golden Config setting's dynamic group and is not among the group's stored members, or is stored and the filter no longer lists it. A group's members are stored, recomputed when the group is saved or by the job `RefreshDynamicGroupCaches`, and Golden Config renders a device under the setting its stored membership gives, with no error, so the device would be rendered under another setting than its filter now gives, or under none (`render.setting.absent` beside it). The message names the devices of each kind, five at most and the rest counted. Refresh the group's stored members: save the group, or run `RefreshDynamicGroupCaches`. A refresh writes no changelog row, so the bracket does not see it; read again after it |
| `group.unchecked` | warning | The dynamic group's name | The dynamic group of a Golden Config setting is of another `group_type` than `dynamic-filter` (a `dynamic-set` or a `static` group), or its filter holds what the reader cannot send as the device list's query: a null, an object, a list within a list, or the key `id`, by which the reader restricts the list to the scoped devices. So its stored members are not held to anything, and a membership stale since its last refresh is not seen; the read goes on. Refresh the group before a read, or give it a filter of text, numbers, booleans and lists of them |
| `render.setting.absent` | error | The device's name (`n1`), or `dcim.device <id>` where it has none | Golden Config answered the device's render 400 `No Golden Config settings found for this device`: the device is in no setting's dynamic group. A group's members are stored, so a device tagged or edited since the group was last refreshed is not among them, and a refresh writes no changelog row the bracket sees. Refresh the stored members of the dynamic group of the setting meant to apply to the device: save the group, or run the job `RefreshDynamicGroupCaches` |
| `render.template.missing` | error | The device's name, or `dcim.device <id>` | Golden Config answered the device's render 400 `Error rendering Jinja template: Jinja template … not found in git repository …`, its words quoted: the template the setting names for the device is not in its template repository. Add the template to the repository, or correct the setting's path to it |
| `render.failed` | error | The device's name, or `dcim.device <id>` | Golden Config answered the device's render 400 in other words beginning `Error rendering Jinja template:`, quoted, cut at 300 characters: the template, or the setting's query, raised, and the cause is in Nautobot's log alone. Correct the template or the query |
| `render.empty` | error | The device's name, or `dcim.device <id>` | Golden Config answered the device's render 200 with an `intended_config` holding no character but whitespace, so the device has no configuration; nothing is defaulted. Correct the template |
| `render.invalid` | error | The device's name, or `dcim.device <id>` | Golden Config answered the device's render 200 with no JSON object holding a text `intended_config`, so the device has no configuration. Report it with Golden Config's version |
| `render.device.unknown` | error | The device's name, or `dcim.device <id>` | Golden Config answered the device's render 400 `Device with id '<id>' not found`, quoted: the device was deleted during the read, or the reader's account may not view it, which Golden Config answers in the same words. It is weighed at the read's close: where the bracket moved, the read is `read.moved` and this is not filed. Read again, or grant the account `view` on `dcim.device` |
| `render.unavailable` | error | The device's name, or `dcim.device <id>` | Golden Config answered the device's render with another status than 200, 400, 401 and 403, given and nothing quoted, or 400 in other words, quoted; a 400 is weighed at the read's close as `render.device.unknown` is. Read again; one that persists is Nautobot's, to report with its answer |
| `probe.context.absent` | error | The context the reader document names (`fylgja-probes`) | The reader document names a configuration context for the probes, and Nautobot lists none of that name, compared exactly; no probe is read, and the rest of the read is judged. Make the context, inactive, or correct the document's `probes` |
| `probe.context.active` | error | The context the reader document names | The context is active (`is_active`), so every device it applies to takes the probes into its configuration context, and a template could render them; no probe is read. Set it inactive |
| `omit.probe.outside_scope` | info | The probe's name (`n1-loop`), or the context's where the probe has none | An end of the probe names a device, compared exactly with the scoped devices' names in Nautobot, that is no device of the scope, or one whose name makes no blueprint name, so its host could be placed nowhere. The probe is left out of the blueprint, a fidelity row `omitted` whose source is `extras.configcontext`, and the rest are read. Tag the device, or name it in the declaration as Nautobot names it |
| `probes.version.unsupported` | error | The context's name | The context's data states a `probes_version` other than `1`, and the core's declaration loader (`fylgja_core.probes`) reads no other; no probe is given. Write the data in version 1's form ([`probes-1.schema.json`](../../formats/probes-1.schema.json)) |
| `probes.invalid` | error | The probe's name, at whose member the loader found the fault; the context's name where the fault is the declaration's own (data that is no mapping, a member missing or unknown) | The context's data violates the declaration's schema, which the loader holds it to after each end's device is made its blueprint name; no probe is given. The message gives the pointer and the loader's words, cut at 300 characters. Correct what they name |
| `probe.name.duplicate` | error | The later probe's name | Two probes of the data share a name, which names one probe; no probe is given. Rename one of them |
| `probe.gateway.outside` | error | The probe's name | An endpoint's gateway is outside its address's prefix; no probe is given. Correct the gateway or the address |
| `probe.address.duplicate` | error | The probe's name | An endpoint's address is another endpoint's host, of this probe or one before it by name; no probe is given. Give each endpoint a host of its own |
